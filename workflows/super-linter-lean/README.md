# Super-Linter Lean Image Workflow

The `super-linter-lean` workflow builds a Super-Linter image that contains only the linters your repository enables, scans it, pushes it to GHCR and records its tag in a repository variable. The [`super-linter`](../super-linter/README.md) workflow then runs that image when its `SUPER_LINTER_CUSTOM_IMAGE` env is set, which cuts the pull-and-start time of the lint job (about 40 seconds against about 110 seconds in the lintsmith benchmark).

The image is generated by [lintsmith](https://github.com/ghwfxlab/lintsmith) from the `VALIDATE_*` flags in `.github/super-linter.env`.

## Source of Truth

- Registry repository: [ghwfxlab/ghwm-registry](https://github.com/ghwfxlab/ghwm-registry)
- Workflow source: [`workflows/super-linter-lean/super-linter-lean.yaml`](./super-linter-lean.yaml)

## What gets installed

After running `ghwm install`, the consumer repository gets:

- `.github/workflows/super-linter-lean.yaml`
- An entry in `ghwm.lock`

It reads `.github/super-linter.env`. It also reads the Super-Linter release from `.github/workflows/super-linter.yaml` unless you set the `SUPER_LINTER_VERSION` repository variable, so you can use it without the `super-linter` workflow.

## How it works

The workflow runs on pushes to `main` that change `.github/super-linter.env`, `.github/workflows/super-linter.yaml` or the workflow itself, and on manual dispatch. It then:

1. Takes the upstream release from the `SUPER_LINTER_VERSION` repository variable (for example `v9.0.0`) or, when it is not set, from the version comment of the `super-linter/super-linter/slim` step in `.github/workflows/super-linter.yaml`.
2. Builds the image with the lintsmith action and smoke-tests it: for every enabled linter it runs the image on Super-Linter's own good and bad fixtures and requires that the good files pass and the bad files fail.
3. Scans the image with Trivy once and prints the HIGH and CRITICAL findings that have a fix. The scan is report-only: only a failure of the scan step itself stops the build.
4. Pushes `ghcr.io/<owner>/<repo>/super-linter-lean` with three tags: `latest`, `<version>` and `<version>-<short sha>` (immutable).
5. Writes the immutable tag to the `SUPER_LINTER_CUSTOM_IMAGE` repository variable.

## Consumer Setup

### 1. Install the workflows

Add to `ghwm.yml` in your repository root:

```yaml
source: ghwfxlab/ghwm-registry
workflows:
  - name: super-linter
    version: 2.0.0
  - name: super-linter-lean
    version: 1.0.0
```

Then run `ghwm install` and commit the files.

### 2. Let the workflow update the variable

A workflow token cannot write repository variables. The workflow uses a GitHub App token for it, with the same `GH_APP_ID` and `GH_APP_PRIVATE_KEY` secrets as the `auto-release` workflow. Give the App the repository permission **Variables: read and write**, and make sure the secrets are available to the repository. The token gets whatever the App is granted (the token action cannot narrow it to variables), so grant the App no more than it needs.

The credentials are required: the job starts by creating the token and fails if the secrets are missing, wrong or expired, or if the App lacks the Variables permission.

### 3. Choose the runner

Like the `super-linter` workflow, the build job runs on GitHub-hosted `ubuntu-24.04`. To use your own runner, edit `runs-on` in `.github/workflows/super-linter-lean.yaml`; `ghwm update` keeps it unless you set `update-runs-on: true` (ghwm v1.13.0). See [Run on your own runners](../super-linter/README.md#example-run-on-your-own-runners).

The runner needs Linux, Docker and outbound access to GHCR and to the Super-Linter release. The workflow sets `TMPDIR` to `RUNNER_TEMP` before the build, so the smoke test's work directory is one the runner's Docker daemon can mount (some self-hosted runners do not share `/tmp` with the daemon).

### 4. Switch the lint job to the lean image

The `super-linter` workflow reads the image from its `env` section, not from the repository variable. In `.github/workflows/super-linter.yaml` point the env value at the variable:

```yaml
env:
  SUPER_LINTER_CUSTOM_IMAGE: ${{ vars.SUPER_LINTER_CUSTOM_IMAGE }}
```

Run the `super-linter-lean` workflow once first (manual dispatch). While the variable is empty, the `super-linter` workflow runs the upstream image chosen by `RUN_SUPER_LINTER_SLIM`. With the variable set, only the `Run Super-Linter Custom Image` job runs. You can also paste an image tag into the env value instead of using the variable; then the variable is not needed and step 2 can be skipped.

### 5. Package access

The image is pushed with the label that links the package to the repository, so the lint job can pull it with its own token. For a private package outside the repository's access list, grant the repository read access to the package.

## Update

Update `ghwm.yml` with a new version, then:

```sh
ghwm update
```

## Remove

Remove `super-linter-lean` from `ghwm.yml`, set `SUPER_LINTER_CUSTOM_IMAGE` back to `""` in the `super-linter` workflow, then:

```sh
ghwm install
ghwm update --prune
```

## Notes and limits

- The image is rebuilt after a change reaches `main`. A pull request that changes `.github/super-linter.env` is still linted with the previous image.
- The workflow's actions, including lintsmith, are pinned to a commit with the release in a trailing comment (`# v0.0.13`), so Dependabot's `github-actions` ecosystem proposes a pull request for each new release. Merge it to take a newer generator.
- Only linters that lintsmith maps can be selected. An unknown `VALIDATE_*` flag fails the build with a message naming it.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `Set the SUPER_LINTER_VERSION repository variable …` | No `SUPER_LINTER_VERSION` variable, and the slim step or its version comment is missing from `super-linter.yaml` | Set the variable, or restore the step as installed by `super-linter` 2.0.0 or later |
| Smoke test reports `FAIL (not-linted)` for a linter | The image lacks that linter or the fixtures do not match the version | Check the generated `plan.json` and the pinned lintsmith version |
| Every linter shows `not-linted` in the smoke test on a self-hosted runner | The Docker daemon cannot see the runner temp directory (`RUNNER_TEMP`) | Make `RUNNER_TEMP` a path the daemon can mount, for example one on the host when the runner itself runs in a container |
| The jobs never start | No runner has the label `ubuntu-24.04` (or the account has no hosted minutes) | Edit `runs-on` in the workflow to your runner label(s) |
| `Generate GitHub App token` fails | `GH_APP_ID` or `GH_APP_PRIVATE_KEY` is missing, wrong or expired | Add or correct the secrets |
| `Record the image …` fails with 403 | The App lacks Variables: read and write, or the installation has not accepted the updated permissions | Grant the permission and accept it on the installation |
